# ADR 0003: идемпотентность через requestId и уникальные индексы

**Статус:** принято.

## Контекст

Повторы при тайм-аутах и повторная доставка запросов не должны создавать дубликаты броней и повторно менять занятость номера.

## Решение

- Внешний запрос на создание бронирования обязан содержать `Idempotency-Key`; значение пишется в `bookings.request_id` с уникальным индексом.
- Повтор с тем же ключом возвращает существующее бронирование без новой записи.
- Гонка двух одинаковых запросов разрешается на уровне БД: проигравший получает `DataIntegrityViolationException` и читает существующую запись.
- Внутренние вызовы используют детерминированные ключи: `UUID.nameUUIDFromBytes(requestId + ":confirm:" + roomId)` и `requestId + ":release"`.
- Hotel хранит обработанные ключи в `processed_requests` и при повторе возвращает сохранённый результат.

## Последствия

- дубликаты исключены на уровне схемы, а не только в коде;
- нужна таблица `processed_requests` и её очистка при необходимости;
- повтор с тем же ключом, но другим телом даёт `IDEMPOTENCY_CONFLICT` (409).

## Альтернативы

- Хранить ключи в Redis: отдельный компонент ради одной таблицы, при текущей нагрузке не нужен.
- Полагаться только на проверку перед вставкой: остаётся окно гонки между проверкой и вставкой.
